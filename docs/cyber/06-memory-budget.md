# 06 · 显存与内存总账

> 本文给出流式档的实测占用、按显存分档的配置表、硬件底线与推荐。
> 证据等级：`A` 本机自实测 ｜ `B` 同机对照实现 ｜ `C` 外部实测 ｜ `D` 推导或出处自报。
> ⚠️ 标 `D` 的是**外推**，必须在下一次实测里被替换成 `A`。

## §1 显存总账

### 1.1 基线

| 项 | 读数 |
|---|---|
| 卡 | RTX 4080 SUPER，`memory.total = 32760 MiB` |
| 引擎自报空闲显存（加载常驻权重后） | **28.20 GiB free** |
| ⇒ **非缓存消耗**（常驻权重 + 上下文 + 激活 + CUDA 上下文） | ≈ **3.79 GiB**（`D`：由 28.20 GiB free 与整卡容量折算） |
| 空闲基线（无引擎，含桌面） | 1160–1203 MiB / 3–7% |

### 1.2 流式档（验收档，reserve 24568）

| 项 | 读数 |
|---|---|
| 引擎那一行（判据线） | `expert cache auto: 28.20 GiB free, 24568 MiB reserved -> 1960 slots` |
| 生效缓存 | `expert cache 2348 slots, 4.20 GiB of VRAM` |
| `pre-filled` | `2348 of 2348 slots` |
| 显存合计（引擎自身 ≈5.2 GiB + 缓存 4.20 GiB） | ≈ **9.4 GiB** |
| 另计常驻投影矩阵 | `250 native projection matrices, 1423.75 MiB of weights` |
| 验证窗口 | `window up to 2 tokens, 43.2 MiB of device buffers (100% VRAM resident)` |
| 每臂跑完回收 | `nvidia-smi memory.used` 回到 **1186–1277 MiB** |

## §2 宿主内存总账（**这是硬前提**）

| 项 | 读数 |
|---|---|
| **专家竞技场（钉住）** | **19,675,480,064 B**（自证行 `cudaHostRegister PORTABLE ok`）；另处记 **18.33 GiB** |
| 文件缓存 | `15 of 16 probe reads from the file cache; 56.0 GiB available, 21.2 GiB of files` |
| ⇒ 模型读取 | **走 OS 文件缓存**（21.2 GiB 模型全部驻留） |
| **每实例 ≈ 20–25 GiB 主机内存** | 这就是**不许并行两个实例**的原因 |
| 本机内存 | 96 GiB（16+32+16+32，2667 MT/s，4 条）；DDR4 双通道理论峰值 ≈42.7 GB/s |
| 实测 | 池子只跑到峰值的 **~1/4**（10–13.6 GB/s） |

| 档 | 内存 | 说明 |
|---|---|---|
| **底线** | **≥ 32 GB** | 钉住银行 19.68 GB + 文件缓存 21.2 GiB 不可能同时轻松容纳 |
| **推荐** | **48–64 GB** | 长上下文（`--kv-resident` 会把 K/V 也钉到内存）与多任务 |
| 不够时 | `--mmap-experts` / `--resident-experts` | 放弃钉住银行退回 mmap，**冷读约慢一倍**（源码注释自报 71.97 vs 34.78 ms/token，`D`） |

**磁盘**：模型 22.75 GB + 包本体 0.27 GB + 系统 ⇒ **建议 ≥40 GB 空闲**；模型会被读进文件缓存 ⇒ **放 SSD**。

## §3 按显存分档的配置表

**槽数估算口径**：本机 4.20 GiB ↔ 1960 槽 ⇒ **约 2.25 MB/槽**（`D`）。
**预计 decode 一律不给绝对值** —— 它同时受 GPU 带宽（随卡）与命中率（随槽数）支配，编一个数出来就是假绿。

| 显存档 | 非缓存消耗后可用（估） | **建议 `--vram-reserve-mib`** | 预计槽数（估） | 调优方向 | 必做自检 |
|---|---|---|---|---|---|
| **8 GB**（8192 MiB） | ≈4.3 GiB | **800–1200** | ~1300–1500 | 槽数不够就压 KV（`--kv int8`）；`--max-context` 先 ≤8192 | 看 `free/reserved/slots` 三数；确认**没有**分页 / 爆显存 |
| **10–12 GB** | ≈6–8 GiB | **1500–2500** | ~2000–3200 | 命中率会明显好于 8 GB 档；**先把 reserve 往下试** | 同上 + 记命中率 |
| **16 GB** | ≈12 GiB | **2500–4000** | ~3500–5500 | 上下文可以放到 16k–32k | 同上 |
| **24 GB** | ≈20 GiB | **4000–8000** | ~5500–9000 | 接近"全常驻"；试 `--max-context 32768+` | 同上 |
| **32 GB** | **28.2 GiB（实测）** | **1500（全常驻）** 或 **24568（限流档）** | **10240 / 1960** | 全常驻档 CPU 池完全不工作，decode 134–136；限流档 CPU 池 5.4 ms | **两条都测，回报两条** |
| 多卡 | — | `--peer-device N` / `--expert-cache-device1..3` | — | 引擎支持第二卡当专家层（P2P） | **完全未验**（`D`） |

**⭐ 两条通用调优顺序（先便宜后昂贵）**：

1. **先把 reserve 往下调**（每次 1000 MiB）直到引擎报的槽数不再涨、或 KV 吃紧 —— 通常比任何代码优化都值钱。
2. 再看**命中率**（`R4 expert-cache hits`）。它 100% 由 **profile 排名 × 槽数** 决定
   （缓存**永不收人**：`0 admitted / cache 100% full`）⇒ 槽数不够时，**换 profile 比调别的东西都有效**。

## §4 可用显存比标称小的时候

**先读引擎那一行，它是唯一的真话**：

```
expert cache auto: X GiB free, Y MiB reserved -> N slots
```

`X` = 加载完常驻权重后**真实可用**的显存（桌面、浏览器、其它程序**全都已经从这里面扣掉了**）
⇒ **不要拿标称显存去推**。

1. **先关掉别的占卡程序**（浏览器硬件加速、壁纸引擎、其它模型 / 游戏）。
2. `X` 小 ⇒ 缓存自动变小 ⇒ 槽数变少 ⇒ 命中率变低 ⇒ CPU 池更忙 ⇒ **变慢，但不会崩**。这是**连续降级**。
3. 若出现**显存不足 / 分页 / 闪退**：把 reserve **调大**。⚠️ 方向别搞反：**reserve 大 = 更安全 = 更慢**。
4. 同时把 `--max-context` 调小，或用 `kv` 压位宽 / `--kv-resident` 挪内存。
5. **内存**不足走 `--mmap-experts` / `--resident-experts`，代价是冷读约慢一倍。

**最小可用显存没有实测过**。机制上缓存可以小到接近 0（全部专家交给 CPU 池），但会很慢。

## §5 两个常被搞错的地方

### 5.1 显存紧张通常**不是** KV 造成的

| 项 | 读数 |
|---|---|
| 4k 上下文 KV（fp16） | **86 MiB** |
| 32k 上下文 KV（fp16） | **690 MiB** |
| 真正吃显存的 | "常驻权重 + 激活"的约 **3.8 GiB**（实测）+ 想给专家缓存的额度 |

每 token 换算：只改 `--max-context`，free 从 **28.20 GiB（4096）** 掉到 **27.61 GiB（32768）**
⇒ **0.59 GiB / 28672 格 ≈ 21.6 KiB 每 token（fp16）**。折算：

| `--max-context` | fp16（引擎默认） | int8 | k8v4 | q4_0（= k4v4） |
|---|---|---|---|---|
| 4096 | **86 MiB** | 43 MiB | 33 MiB | 22 MiB |
| 8192 | 173 MiB | 86 | 66 | 43 |
| 32768 | 690 MiB | 345 | 267 | 173 |
| 131072 | 2.76 GiB | 1.38 | 1.07 | 0.69 |
| 262144 | 5.52 GiB | 2.76 | 2.13 | 1.38 |

每格字节（引擎 `--help`）：

| 档 | 每格 | 相对 fp16 | 说明 |
|---|---|---|---|
| `fp16` | 2112 B | 100% | 引擎默认 |
| `int8` | 1056 B | 50% | int8 码 + 每 64 值一个 fp16 scale |
| `k8v4` | 816 B | 39% | INT8 K + 旋转 Q4_0 V；**不能与 `--kv-resident` 同用** |
| `q4_0` | 528 B | 25% | K/V 都 4-bit，经 Hadamard 旋转 |

### 5.2 `--kv-resident` 真的能腾出显存（**已实测**）

`--kv-resident N` = 每层留 N 格在显存（下限 **20480**），整份 K/V 放**钉住的宿主内存**。

| 臂 | 引擎自报空闲显存 | 引擎原话 |
|---|---|---|
| `--max-context 32768`（不开） | 27.61 GiB | — |
| 同上 **+ `--kv-resident 20480`** | **27.84 GiB（+0.23）** | `KV streaming: 20480 of 32768 cells per QSA layer in VRAM, the K/V in 0.63 GiB of pinned RAM` |
| `--max-context 131072`（不开） | 25.59 GiB | — |
| 同上 **+ `--kv-resident 20480`** | **27.70 GiB（+2.11）** | `KV streaming: 20480 of 131072 cells per QSA layer in VRAM, the K/V in 2.50 GiB of pinned RAM` |

⇒ **128k 上下文下：花 2.50 GiB 内存，换回 2.11 GiB 显存。**
（引擎 help 里写的是 "per QSA layer" —— 那是旧措辞；**对 Cyber 实测有效**。先前"很可能无效"的判断已被推翻。）

## §6 出处

**测量环境**：本机 = RTX 4080 SUPER（32760 MiB）+ i7-13790F + 96 GiB DDR4-2667；除标明外均为 `A` 级自实测。

| 结论 | 证据 |
|---|---|
| `28.20 GiB free`、整卡 32760 MiB、非缓存消耗 ≈3.79 GiB | 引擎自报行 + 整卡容量折算 |
| 流式档 `1960 slots` / `2348 slots, 4.20 GiB of VRAM`、`pre-filled`、借槽 812、验证窗口 43.2 MiB、跑完回收 1186–1277 MiB | 本机引擎日志与 `nvidia-smi` 逐臂采样 |
| 常驻档 `1500 -> 10240 slots` / `18.32 GiB`、合计 ≈23.5 GiB、未见 OOM | 同上 |
| `21999 / 20798.80 / 696 / 688 MiB` | 外部 llama.cpp 服务端自报的 CUDA0 buffer 与本机 `nvidia-smi` 采样 |
| 宿主银行 `19,675,480,064 B`、`cudaHostRegister PORTABLE ok` | 引擎自报行 |
| 文件缓存 `56.0 GiB available, 21.2 GiB of files`、每实例 20–25 GiB、不许两实例 | 引擎自报的 probe 行 + 本机内存采样 |
| 96 GiB / 2667 MT/s / 42.7 GB/s 理论峰值 | 本机硬件信息 + 带宽折算 |
| 内存底线 ≥32 GB、推荐 48–64 GB、磁盘 ≥40 GB / SSD | 本机实测占用 + 引擎源码注释 |
| mmap 冷读慢一倍（71.97 vs 34.78 ms/token） | 引擎源码注释自报 |
| 按显存分档表、2.25 MB/槽、两条调优顺序 | §3；2.25 MB/槽为折算值（`D`） |
| 可用显存比标称小、5 条调整规则、最小可用显存未实测 | §4；引擎自报的 `free` 行是本条唯一真话 |
| KV 86 MiB / 690 MiB、21.6 KiB 每 token、四个位宽表 | 只改 `--max-context` 看 `free` 变化的单变量实测 + 引擎 `--help` 的每格字节 |
| `--kv-resident` 四行实测（+0.23 / +2.11 GiB） | 本机同配置单变量臂（`--max-context` × `--kv-resident` 两两对照，§5.2） |
